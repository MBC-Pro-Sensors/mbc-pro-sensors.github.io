MBC Sharpshooter Vision × LEGO SPIKE App (Python)

Read Sharpshooter Vision with SPIKE App Python in three steps

The LEGO SPIKE App (Education) runs Python too, with no firmware change. In the App, Sharpshooter Vision is a color sensor, and the App cannot import your own files, so the order is: first paste the reading helper at the top and pick the camera mode, then create an object and name the camera, then call update() once per loop and call its functions with that name. Work down the steps on the left and watch the program grow on the right; drag the blobs, papers, blocks or line in the simulated camera view to see what the program prints.

v1 not yet hardware-verifiedThe value layout is final and passed computer tests; real-hardware numbers (fps, line thresholds, I2C pins) may change after hardware testing.

1

Paste the helper, pick the camera mode

A SPIKE App Python project is a single file and cannot import your own .py, so paste the whole "reading helper" at the very top (its first lines say so: copy it as is). Without it the hub does not know UniCamApp and stops with NameError.

  1. Open the LEGO SPIKE App (Education, yellow SPIKE Prime hub), create a project and choose "Python".
  2. Paste the program marked ① on the right at the top (only the first helper line shows; press "Show helper" to see it all, and "Copy program" always copies everything). The helper alone: MBC_UniCam_App_helper.py (open it in a text editor and copy all; the file has Chinese and English comments).
  3. Plug the camera into any port A–F; the hub powers it. The camera needs the SPIKE firmware (the same firmware tells the App and Pybricks apart by itself).
  4. Pick the camera mode: choose the camera mode and sub-option in the camera's MODE menu, and click the same mode number below (mode number = camera mode × 10 + sub-option).
2

Create the object: name the camera

A robot can have several sensors, so you "create an object": tell the helper which port the camera is on (port.C comes from from hub import port) and which mode it is in, and give it a name. You use that name for every reading.

Which port is the camera on?

The second number is the mode number from step 1; switch the camera menu to the same mode (the App cannot read the camera's mode, so the helper splits the numbers by what you wrote; a mismatch gives nonsense).

3

update() every loop, then use a function

App programs go in async def main(): and runloop.run(main()) starts them; wait with await runloop.sleep_ms(100) (not Pybricks' wait()). Each loop first reads once with cam.update(), then uses "name + dot + function". Functions are grouped by camera mode; dashed ones belong to another mode (clicking one switches the mode for you).

Simulated camera view: drag things in the picture and watch the output change

The view is a sketch: values come straight from where things are on screen (X 0–159 left→right, Y 0–119 top→bottom, area % = width × height ÷ whole picture); a hue code is the color the paper or block really has (red 0, yellow 40, green 80, blue 160, purple 200, white table 244, black tape 252). It is not the camera's own algorithm, and real numbers vary with the light. Color tracking assumes 4 colors were taught on the camera: color 1 red, 2 green, 3 blue, 4 yellow. In object detection you pick each shape yourself (the camera does not judge it here); objects 1, 2… are sorted by area, largest first; X, Y is the shape's centroid (white dot), the dashed box is its bounding box, and the angle is the rotation you set.

An example for every function

Every function has an example you can drop into main() (name cam); the badge shows which modes it works in. "Try it" jumps to step 3 (and switches the mode if needed).

Bytes 8–15: values the helper cannot readnot yet tested

    
The camera sends 16 bytes each time. The App's color_sensor.color(), reflection() and rgbi() only get the first 8, which is what the helper uses. The other 8 bytes (table below) might be readable with App Python's device.data(), but this is not yet verified on hardware (task #77): how many numbers it returns and in what format is unknown, so this page does not show how to split them and the helper does not use them. To use these values now, switch to Pybricks MicroPython (same camera, same firmware; with the Pybricks firmware on the hub they can be read). To peek at what device.data() returns when you test on a hub, try these lines (unverified: it may fail or return only a few numbers; please tell us what you get):

    
import device
from hub import port
import runloop


async def main():
    while True:
        print(device.data(port.C))   # not yet hardware-tested: count and format unknown
        await runloop.sleep_ms(500)

runloop.run(main())

  

  

    
Good to know

    
    
      
  1. Call update() every loop. All helper functions split the 8 bytes from the last update(); without it the values never change (they start as all 0).
    2. 
      
  2. The mode number must match the camera menu. The App cannot read the camera's mode, so the helper splits by UniCamApp(port.C, mode); object functions in the wrong mode raise ValueError, the others just give meaningless numbers.
    3. 
      
  3. This is SPIKE App 3 style, not Pybricks. Ports are port.C from from hub import port (not Port.C), and waiting is await runloop.sleep_ms() (not wait()), so Pybricks programs cannot be pasted in. Python in the Robot Inventor (home) App is not verified yet; this page is for the Education App.
    4. 
      
  4. Positions are grid cells, not pixels. Modes 13 and 14 use a 16×12 grid (pixel ≈ cell×10−5); modes 11, 12 and object list 51 use 8×6 (pixel ≈ cell×20−10); (0, 0) = not seen. Only object 1 in mode 52 is in pixels. Y top = small; line offset: left = negative, right = positive (looking forward from behind the robot).
    5. 
      
  5. The helper reads bytes 0–7 only. Step 1 lists what each mode gives; for the rest (counts, areas, mid offset, flags…) see "Bytes 8–15" above or use Pybricks MicroPython. Colors are taught on the camera; the program cannot change them.
